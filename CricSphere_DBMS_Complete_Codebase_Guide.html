1. Project Overview & 3-Tier Architecture

CricSphere is a full-stack Sports Database Management System built specifically for cricket tournament administration, match scheduling, live ball-by-ball scoring, player statistics management, and honors leaderboards.

Three-Tier Architectural Model

┌─────────────────────────────────────────────────────────────────────────────┐ │ 1. PRESENTATION TIER (Frontend - React 19 + Vite) │ │ URL Routing: /stastics, /stadium, /tournaments, /matches, /leaderboards │ │ Components: Scorecard, Scorer Console, Leaderboards, Venue Cards │ └──────────────────────────────────────┬──────────────────────────────────────┘ │ HTTP Requests (JSON over REST) ▼ ┌─────────────────────────────────────────────────────────────────────────────┐ │ 2. APPLICATION TIER (Backend - Node.js + Express Server) │ │ Port: 5000 | Routes: /api/matches, /api/players, /api/tournaments, etc. │ │ Middleware: JWT Authentication & Role-Based Access Control │ └──────────────────────────────────────┬──────────────────────────────────────┘ │ SQL Queries & Stored Procedures (mysql2) ▼ ┌─────────────────────────────────────────────────────────────────────────────┐ │ 3. DATA TIER (Database - MySQL Relational Database) │ │ Port: 3306 | Schema: new_cricket_db │ │ Tables: tournament, teams, player, matches, match_balls, venue, stats │ └─────────────────────────────────────────────────────────────────────────────┘
  • Presentation Tier (Client): Built with React 19. It communicates asynchronously with the backend using the Fetch API and synchronizes browser URLs with the HTML5 History API (without reloading).
  • Application Tier (Server): Built with Express.js. It authenticates users, enforces security roles (Player, Organizer, Admin), and runs SQL queries against MySQL.
  • Data Tier (Database): A normalized MySQL relational database maintaining ACID guarantees, primary keys, foreign keys, and stored procedures for complex multi-table transactional updates.

2. Database Schema & Relational Modeling (Data Tier)

The database schema stores all entities of a real-world cricket ecosystem. Below is the relational mapping of the key database tables:

Table Name Primary & Foreign Keys Description & Role in DBMS
tournament PK: tournament_id
FK: type_id → tournament_type		 Master table for tournaments (e.g. Southern Cup T20). Contains start date, end date, host country, and format reference.
teams PK: team_id
FK: country_id → country		 National and club teams. Contains team name, coach, founded year, and foreign key to country.
player PK: player_id
FK: team_id → teams
FK: country_id → country		 Master directory of all 124+ athletes. Stores first name, last name, jersey number, batting style, bowling style, and playing role.
venue PK: venue_id
FK: country_id → country		 Directory of 20 international cricket stadiums. Stores venue name, city, seating capacity, and pitch type (Spin, Pace, Flat).
matches PK: match_id
FK: tournament_id, venue_id
FK: team1_id, team2_id		 Scheduled, Live, or Completed fixtures. Tracks toss decision, winner team, winning margin, win type, and Player of the Match.
match_balls PK: ball_id
FK: match_id → matches
FK: striker_id, bowler_id		 Granular ball-by-ball deliver log. Records over number, ball number, runs, extras, extra type, wicket flag (is_wicket), and commentary text.
player_match_stats PK: stat_id
FK: match_id, player_id, team_id		 Individual scorecard per match. Stores runs scored, balls faced, boundaries (4s/6s), dismissal mode, overs bowled, runs conceded, and wickets taken.
users PK: user_id
FK: player_id → player (optional)		 Authentication credentials with bcrypt password hash and role (Player, Organizer, Admin).
💡 DBMS Examiner Note: Primary Key & Foreign Key Constraints
All relationships enforce referential integrity. For example, in matches, team1_id and team2_id reference teams(team_id). A match cannot exist without valid teams, and a ball cannot be logged without valid player and match foreign keys.

5. Detailed Walkthrough of Core Features & Solved Challenges

1. How the Live Score & Wicket Logic Works

User clicks 'W' (Wicket) in LiveMatchCenterView │ ▼ Calls api.scoreBall(matchId, { is_wicket: 1, striker_id: 14, bowler_id: 107 }) │ ▼ MySQL executes sp_ScoreBall: 1. Inserts row into `match_balls` with is_wicket = 1, commentary = 'OUT!...' 2. Updates `player_match_stats` for striker: is_out = 1, dismissal_type = 'Caught' 3. Updates `player_match_stats` for bowler: wickets_taken = wickets_taken + 1 │ ▼ Frontend receives updated match state: 1. Wickets calculated accurately: Math.min(10, Math.max(battingOut, bowlerWkts, ballWkts)) 2. Striker auto-advances to the next available batsman in team squad 3. Dismissed player marked ❌ (Out) and disabled in dropdown

The Problem Solved: Previously, wickets were only calculated by counting rows in team1Batting where is_out = 1. Because the striker was never auto-rotated when a wicket fell, no new rows were created for subsequent batsmen, causing the live score to stall at 2 wickets. The new algorithm accurately counts all fallen wickets from balls, bowling figures, and batting rows, while advancing the batsman in the squad automatically.

2. The Live Points Table & Net Run Rate (NRR) Formula

In tournament standings, teams are ranked by Points first, and then by Net Run Rate (NRR). NRR is computed inside the database query as: 

NRR = (Total Runs Scored / Total Overs Faced) - (Total Runs Conceded / Total Overs Bowled)

Wins award 2 points, ties award 1 point, and losses award 0 points.

7. Top 10 Viva & Interview Questions with Direct Answers

Q1: What is the main objective of this project?

Answer: To design and implement a relational database management system that automates cricket tournament administration, match scheduling, live ball-by-ball score tracking, player career metrics, and honors board leaderboards.

Q2: Why use a Relational Database (MySQL) rather than NoSQL (MongoDB)?

Answer: Cricket data is highly structured and relational. A match involves two specific teams, at one specific stadium, with 22 specific players. Relational integrity (Primary Keys, Foreign Keys, ACID transactions) guarantees that a ball recorded updates the bowler, batsman, match total, and tournament points table without data anomalies.

Q3: What are the primary keys and foreign keys in the live scoring module?

Answer: In match_balls, ball_id is the Primary Key. The Foreign Keys are match_id (referencing matches), striker_id (referencing player), and bowler_id (referencing player).

Q4: How do you prevent unauthorized users from editing live scores?

Answer: Through Role-Based Access Control (RBAC). The Express server uses the requireOrganizerOrAdmin middleware to inspect the JWT token in the HTTP Authorization header. Only users with the role 'Organizer' or 'Admin' can call the /score-ball and /complete endpoints.

Q5: How does the application update the URL path without reloading the webpage?

Answer: Using the HTML5 History API. When a user clicks a nav tab or card, window.history.pushState({}, '', targetPath) updates the browser's address bar, and React conditionally renders the corresponding view component.

Q6: What happens when 10 wickets fall in a live match?

Answer: The system caps total wickets at 10. When the 10th wicket is recorded, the striker rotation logic detects that no eligible batsmen remain in the squad, disables the Wicket button, and alerts the scorer that the innings is complete (All Out).

Q7: How are batting averages and strike rates calculated?

Answer: Batting Strike Rate is (Runs Scored * 100) / Balls Faced. Batting Average is Runs Scored / Times Dismissed (is_out). If a player has never been dismissed, their total runs represent their average.

Q8: How does the database handle stored procedures?

Answer: We use MySQL stored procedures like sp_ScoreBall for complex multi-table transactional writes where inserting a ball delivery, updating player stats, and setting match status must occur atomically.

Q9: How did you implement mobile responsiveness?

Answer: Through pure CSS media queries (@media (max-width: 992px), 768px, and 480px). The scoreboard banner stacks vertically, multi-column grids collapse to single columns, and the navigation bar transforms into a mobile hamburger drawer.

Q10: What is the connection pooling strategy used in Node.js?

Answer: In server/db.js, we use mysql.createPool() with connectionLimit: 10. This reuses database connections across incoming HTTP requests rather than opening and closing a new TCP socket on every single query.
